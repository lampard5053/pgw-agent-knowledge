# เคสที่พบบ่อย

รวบรวมเคสตัวอย่างจริงที่ทีม Support เจอ พร้อมการวิเคราะห์ — ดูกลไก `/md` และโครงสร้างห้อง Telegram ที่ [ภาพรวม](index.md), ดูตารางสรุป Status ทั้งหมดที่ [Transaction Status Reference](status-reference.md)

## ดัชนีเคสตัวอย่างทั้งหมด

| เคส | ชื่อเรื่อง | ประเด็นหลัก | Status ที่เกี่ยวข้อง |
|---|---|---|---|
| [เคสที่ 1](#เคสที่-1) | unknown_deposit / unmatch (ธรรมดา) | ลูกค้าโอนเข้าไม่ตรง pre-transaction → แก้ด้วย Match | Unmatched → Success |
| [เคสที่ 2](#เคสที่-2) | ลูกค้าคนเดียวกันผูกกับ 2 ร้านค้าด้วยบัญชีเดียวกัน | บัญชีธนาคารถูกใช้ร่วมกันทั้งฝั่งลูกค้าและฝั่งร้าน → แก้ด้วย Manual Success | Unmatched → Manual_success |
| [เคสที่ 3](#เคสที่-3) | Withdraw ค้างสถานะ Created นาน 2 เดือน | Payment Channel ถูก Suspend เพราะ Bot ติด CAPTCHA + เคสเดี่ยวที่ Job หลุดคิว | Created, Failed |
| [เคสที่ 4](#เคสที่-4) | ลูกค้าเปลี่ยนใจกลางทาง (ชัยวัฒน์) | พฤติกรรมลูกค้าที่ทำให้เกิด Unmatched สะสม ไม่ใช่บั๊กระบบ | Created, Canceled, Expired, Unmatched |

## เคสที่ 1 — unknown_deposit / unmatch (ธรรมดา) {: #เคสที่-1 }

เคสตัวอย่างจริงที่ได้เห็น (ร้านค้า UOK168, 27/07/2026):

1. **ลูกค้าโอนเงิน** ฿130.00 จากบัญชี SCB "สาวดี มูลประภา" ไปยังบัญชี KTB ของร้าน "บริษัท มิโนเรน จำกัด" เวลา 11:54 — ระบบจับคู่อัตโนมัติไม่ได้ กลายเป็น `unknown_deposit`
2. ลูกค้า/พนักงานร้านส่งรูปสลิป + คำสั่ง `/md 019fa1eb-b885-7000-ba84-bf27d3821b0d` เข้าห้อง `[JoinPay][Support] UOK168`
3. บอทตอบกลับทันทีในห้องนั้น: *"🖐 ไม่สามารถจับคู่ธุรกรรมได้ กำลังส่งเรื่องให้แอดมินตรวจสอบครับ"*
4. บอท forward เคสเข้า `[Ticket] JoinPay` พร้อม tag เคส `unknown_deposit`, สถานะ `open`
5. เจ้าหน้าที่ (พบใน log ว่าคือ `@[PM][TS]-Lady Sherry-`) เปิด **Admin Console → Payment → Transactions** ค้นด้วย UUID เดียวกันตรงๆ (ผ่านช่อง "Search Transactions")
6. พบ transaction จริงในระบบ ตรงกับยอด/เวลาในสลิปทุกจุด (Deposit ฿130.00, From: 2842378182 สาวดี มูลประภา SCB, To: 0170754324 บริษัท มิโนเรน จำกัด KTB, เวลา 11:53)
7. เจ้าหน้าที่กด **Match** จากเมนู Transaction Operations (ดู [Admin Console → Transactions](../console/payment/transactions.md)) — ผลลัพธ์ที่เห็นตรงๆ ในตาราง: **Type เปลี่ยนจาก "Unknown Deposit" เป็น "Deposit" ปกติ และ Status กลายเป็น "Success"** ทันที (ไม่ใช่ "Manual Success" ซึ่งเป็นปุ่มแยกต่างหากในเมนูเดียวกัน — คาดว่าสำรองไว้ใช้กรณีอื่นที่ไม่ใช่การจับคู่แบบ formal)
8. บอทตอบกลับในห้องร้านค้า: *"แอดมินอนุมัติยอดเรียบร้อยครับ"* — ปิดเคส

!!! danger "ยืนยันความเชื่อมโยงกับเอกสาร Admin Console เดิม"
    เคสนี้ยืนยันตรงๆ ว่า flow "unknown_deposit → ตรวจสอบด้วยมือ → Match" ที่เคยบันทึกไว้จากการสำรวจ UI ล้วนๆ ใน [Admin Console → Transactions](../console/payment/transactions.md) **ตรงกับการทำงานจริงของทีม Support ทุกขั้นตอน** รวมถึงยืนยันว่า UUID ที่ใช้ค้นหาในช่อง "Search Transactions" คือ pre-transaction UUID เดียวกับที่ใช้ในคำสั่ง `/md`

!!! danger "ยืนยันแล้ว — Match เปลี่ยนทั้ง Type และ Status พร้อมกัน"
    `unknown_deposit` เป็นแค่**สถานะชั่วคราวก่อนจับคู่ได้** ไม่ใช่ Type ถาวร — พอกด **Match** สำเร็จ ระบบรีคลาสธุรกรรมนั้นให้กลายเป็น **Type: Deposit** (ปกติ) และ **Status: Success** พร้อมกันทันที (**ไม่ใช่ "Manual Success"**) ยืนยันจากการเห็นทั้งตารางและ Payment Receipt modal ของ transaction เดียวกัน (`019fa1eb-b885-7000-ba84-bf27d3821b0d`) ตรงกัน

## เคสที่ 2 — ลูกค้าคนเดียวกัน ผูกกับ 2 ร้านค้าด้วยบัญชีเดียวกัน {: #เคสที่-2 }

ตัวอย่างจริงอีกเคส (TX `019fae27-81e5-7000-972d-7d7f7a5cfef3`, 29/07/2026): ลูกค้าชื่อ **"จรวยพร เวียงสมุทร"** (เลขบัญชี `0583442960` KBNK) โอนเงิน **฿1,500.00** เข้าบัญชี `0170739155` (KTB) — ระบบจับคู่อัตโนมัติไม่ได้ กลายเป็น `unknown_deposit` เช่นเดียวกับเคสแรก แต่**สาเหตุซับซ้อนกว่าเดิม 2 ชั้น**:

1. **บัญชีปลายทางถูกใช้ร่วมกันหลายร้าน** — บัญชี `0170739155` เดียวกันนี้ยังรับเงินให้ merchant อื่นอีกหลายราย (`marang777`, `popsloth`, `br-x89` ในตัวอย่างที่เจอ) — ระบบมองแค่เลขบัญชีปลายทางอย่างเดียวไม่รู้ว่าเป็นของร้านไหน
2. **ตัวลูกค้าเองก็ผูกกับ 2 ร้านค้าด้วยบัญชีเดียวกัน** — ค้นหน้า [Merchant Customers](../console/merchant/customers.md) ด้วยเลขบัญชี `0583442960` พบว่า **"จรวยพร เวียงสมุทร" ลงทะเบียนเป็น Customer อยู่ทั้งกับ merchant `UFABET5588` และ `br-5588`** ด้วยบัญชีธนาคารใบเดียวกันเป๊ะ

!!! danger "แม้จะรู้ว่าบัญชีปลายทางไหน ระบบก็ยังไม่รู้ว่าลูกค้าตั้งใจเติมเครดิตเว็บไหน"
    ต่อให้แก้ปัญหาข้อ 1 ได้ (รู้ว่าบัญชีนี้เป็นของกลุ่ม merchant ไหน) **ก็ยังไม่พอ** เพราะลูกค้าคนนี้มีบัญชีอยู่กับ **2 เว็บที่ต่างกัน** โดยใช้บัญชีธนาคารใบเดียวกันสมัครทั้งคู่ — ระบบจึงไม่มีทางรู้อัตโนมัติว่าเงินก้อนนี้ลูกค้าตั้งใจเติมให้เว็บไหนกันแน่ระหว่าง `UFABET5588` กับ `br-5588`

    ผลลัพธ์สุดท้าย: transaction นี้ถูกกำหนดเป็นของ merchant **`br-5588`** ผ่านการกด **Manual Success**

### แล้วแอดมินรู้ได้ยังไงว่าคือ br-5588 ไม่ใช่ UFABET5588?

!!! danger "ยืนยันแล้ว — รู้จากห้อง Telegram ที่ลูกค้าส่งสลิปเข้ามา"
    พบ screenshot ห้อง **`[JoinPay][Support] br-5588`** ของเคสนี้โดยตรง — ลูกค้า (Telegram user "Teddy Bird") ส่งสลิปโอนเงิน ฿1,500 พร้อมคำสั่ง `/md 019fae27-cbd7-7000-8475-c8e0d5803261` **เข้าห้อง Support ของ br-5588 โดยเฉพาะ** (ไม่ใช่ห้องของ UFABET5588)

    **ยืนยันสมมติฐานเดิม 100%:** แอดมิน**ไม่ได้เดาหรือคำนวณเองว่าคือ merchant ไหน** — แต่รู้จาก**ห้อง Telegram ที่ลูกค้าเลือกส่งสลิปเข้ามาโดยตรง** ความจำเพาะของช่องทางที่ลูกค้าใช้ติดต่อ คือข้อมูลบริบทที่บอกทุกอย่าง ไม่ต้องอาศัยระบบช่วยแยกแยะเลย

!!! tip "เจอหลักฐานเสริม — UUID ใน /md ชี้ไปที่ pre-transaction/Deposit เดิม ไม่ใช่ Unknown Deposit โดยตรง"
    UUID ที่ใช้ในคำสั่ง `/md` ของเคสนี้ (`019fae27-cbd7-7000-8475-c8e0d5803261`) **ตรงกับ ID ของ transaction "Deposit/Expired"** (ยอด ฿1,000 ไปบัญชี `0170754480`) ที่เจอไว้ก่อนหน้า **ไม่ใช่ ID ของ Unknown Deposit** (`019fae27-81e5-...-7a5cfef3`, ยอด ฿1,500 ไปบัญชี `0170739155`) ที่เป็นเงินจริงที่เข้ามา — สนับสนุนสมมติฐานเรื่อง order ID ซ้ำกันด้านล่างอย่างมาก: **ลูกค้ารู้จัก UUID จากคำขอฝากเงินเดิมของตัวเอง (ที่ระบบสร้างให้ตอนกดฝาก) เท่านั้น ไม่รู้จัก ID ของ Unknown Deposit ที่เป็น record ภายในที่ระบบสร้างขึ้นเองทีหลัง** — แอดมินต้องเป็นคนเชื่อมโยง 2 record นี้เข้าด้วยกันเอง

    สลิปยังยืนยันด้วยว่าปลายทาง "บริษัท เอ็นเอสพี ศิไทย จำกัด" ตรงกับชื่อใน Payment Channel `joinpay-ktbbiz-**NSP**-0170739155` (คำว่า "NSP" ในชื่อ channel ย่อมาจากชื่อบริษัทเจ้าของบัญชีจริง)

!!! tip "เชื่อมกับหลักฐานที่พบก่อนหน้า — order ID ซ้ำกันระหว่าง 2 transaction"
    เจอ transaction อีกตัว (`019fae27...d5803261`) ที่มี **order ID เดียวกัน** (`D58X50435TBGUZOOJ5C3`) กับเคสนี้ แต่เป็น Type "Deposit" ปกติ สถานะ **Expired**, ยอด ฿1,000.00, ปลายทางบัญชี `0170754480` (คนละบัญชีกับที่โอนจริง) — **คาดว่า** นี่คือ pre-transaction ตัวจริงที่ลูกค้าควรจะโอนตาม (฿1,000 เข้าบัญชี A) แต่ลูกค้ากลับโอนจริง ฿1,500 เข้าบัญชี B แทน ทำให้คำขอเดิม Expired ไปเอง ส่วนเงินจริงกลายเป็น Unknown Deposit ที่ต้องแก้ด้วยมือ — ยังไม่ยืนยัน 100% ว่า 2 transaction นี้เกี่ยวข้องกันแบบนี้จริง

## เคสที่ 3 — Withdraw ค้างสถานะ Created นาน 2 เดือน {: #เคสที่-3 }

พบ transaction ประเภท **Withdraw จำนวน 63+ รายการ ค้างสถานะ Created ตั้งแต่ 27 พ.ค. ถึง 30 มิ.ย. 2569** กระจายข้ามหลาย merchant ที่ไม่เกี่ยวข้องกันเลย (`no7_city169`, `NEO_fun189x`, `sen-sm`, `pk-678`, `lasvip` ฯลฯ)

!!! danger "สาเหตุที่ 1 — Payment Channel ต้นทางถูก Suspend เพราะ Bot ติด CAPTCHA"
    ตรวจสอบ [OpsDash → Bank Account](../opsdash/bank-accounts.md) ของบัญชีต้นทาง `7231054442` (`joinpay-kbiz-cresovation-7231054442`, Kind **KBIZ**) พบสถานะ **Status: Suspend, Flag: Captcha** ตรงๆ — บอทที่ควบคุมมือถือบัญชีนี้ติดหน้าจอ CAPTCHA แก้เองไม่ได้ ต้องรอคนแก้ด้วยมือ

    เมื่อไล่ดูประวัติ transaction ของบัญชีนี้ พบจุดตัดชัดเจนวันที่ **7 ก.ค.**: รายการก่อน ~07:31 น. **Success หมด**, รายการตั้งแต่ ~07:34 น. เป็นต้นไป **Failed หมดทุกแถวต่อเนื่อง** — นี่คือช่วงเวลาที่บัญชีเริ่มติด CAPTCHA จริง

!!! danger "สาเหตุที่ 2 — พบว่า 'Created' ไม่เท่ากับ 'บัญชีเสีย' เสมอไป"
    TX ตัวอย่าง `019e6698...a8990f80` (merchant `lasvip`, ฿100.00) ค้าง Created ตั้งแต่ **27 พ.ค.** — แต่ช่วงเวลานั้นบัญชีเดียวกันนี้**ยังทำงานปกติดี** (รายการข้างเคียงในเวลาใกล้เคียงกันมาก Success รัวๆ ต่อเนื่อง) แปลว่าไม่ใช่บัญชีเสียทั้งระบบ แต่เป็น**เคสเดี่ยวที่ Job หลุดหายจากคิวไปเฉยๆ ไม่มี auto-retry**

    **สรุปความต่างที่ชัดขึ้น:** **"Created" = ไม่เคยมี Job ไปแตะเลยสักครั้ง (orphan)** ส่วน **"Failed" = มี Job พยายามทำแล้วจริง แต่เจอ error ระหว่างทาง** — คนละกลไกกัน ไม่ใช่แค่ระดับความรุนแรงต่างกัน ดูตารางเทียบ Status เต็มที่ [Transaction Status Reference](status-reference.md)

!!! question "สมมติฐานที่ยังไม่ยืนยัน — เลขบัญชีปลายทางผิดปกติทำให้บอทค้าง"
    บัญชีปลายทางของ TX ที่ค้าง Created (`13881353831388...`) มีลักษณะยาว/ซ้ำผิดปกติ (ดูเหมือนตัวเลขชุดเดิมซ้ำตัวเอง) — **คาดว่า** อาจเป็นข้อมูลเพี้ยนตั้งแต่ต้นทาง ทำให้ validation ล้มเหลวตั้งแต่ก่อน Job จะถูก dispatch ไปถึงบอทจริง (จึงไม่มีการรายงาน error กลับมาเป็น Failed) — ยังไม่ได้เปิด Payment Receipt ดูเลขเต็มมายืนยัน

## เคสที่ 4 — ลูกค้าเปลี่ยนใจกลางทาง ทำให้เกิด Unmatched สะสม (ชัยวัฒน์) {: #เคสที่-4 }

ลูกค้าคนหนึ่ง (บัญชี `020255927484` "ชัยวัฒน์") มีประวัติสร้างคำขอฝากซ้ำๆ กับ merchant เดียว (`ropopza24z`): **Expired 3 ครั้ง, Canceled 1 ครั้ง, สำเร็จแค่ 1 ครั้ง** จาก 7 ครั้งที่พยายามทั้งหมด

เหตุการณ์ล่าสุด: สร้างคำขอฝาก ฿100 (Canceled เกือบทันที) → สร้างคำขอฝาก ฿100 ใหม่อีกรอบ (ยังค้าง Created) → แต่ดันโอนเงินจริงแค่ **฿80** (เปลี่ยนใจกลางทาง) → เงิน ฿80 นั้นไม่ตรงกับคำขอไหนเลย กลายเป็น **Unknown Deposit ค้างถาวร**

!!! danger "สรุป — backlog Unmatched จำนวนมากไม่ใช่บั๊กระบบ แต่คือพฤติกรรมลูกค้า"
    ตัวอย่างนี้ยืนยันว่า backlog Unmatched จำนวนมากสะท้อน**พฤติกรรมลูกค้าจริงที่เปลี่ยนใจ/โอนไม่ตรงยอดที่คำขอกำหนด** เป็นเรื่องปกติที่เกิดซ้ำกับลูกค้าเดิมได้หลายครั้ง — ยอดเล็กๆ มักไม่มีคนมาเคลม เพราะลูกค้าเองก็ไม่ได้สนใจกลับมาแก้ไขแล้ว
